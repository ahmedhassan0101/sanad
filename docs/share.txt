# A3 — Typography

هنا أنا لا أريد نعيد اختراع الخطوط. عندنا اتجاه واضح بالفعل، وهنحوّله إلى **نظام Typography قابل للتنفيذ**.

## 1. الخطوط

### Arabic — Tajawal

نستخدم:

**Tajawal**

للواجهة العربية بالكامل.

لماذا؟

* واضح جدًا في الـ UI.
* مناسب للنصوص الصغيرة.
* شكله حديث لكن مش Techy زيادة.
* لا يحمل طابعًا دينيًا أو زخرفيًا مباشرًا.
* مناسب لطبيعة سَنَد المؤسسية.

### Latin / Numbers — Inter

نستخدم:

**Inter**

للإنجليزية والأرقام.

خصوصًا:

* الأرقام الكبيرة.
* KPIs.
* التواريخ.
* النسب.
* الأرقام المالية.
* البيانات الجدولية.
* المصطلحات الإنجليزية التقنية.

وده يعطي فصلًا واضحًا بين:

**Arabic UI ↔ Data / Numbers**

بدون ما نحس إن النظام يستخدم خطين بشكل عشوائي.

---

# 2. قاعدة مهمة جدًا

مش معنى إننا بنستخدم Inter للأرقام إن كل رقم في الصفحة لازم يتحول إلى Inter.

القاعدة:

> **Typography follows the content role, not the character's language فقط.**

مثلًا:

**عدد الطلاب**

`248`

هنا الرقم KPI → **Inter 700**

لكن:

**تم تسجيل الحضور الساعة 10:30**

الوقت جزء من النص → ممكن يبقى ضمن Typography السياق العربي.

---

# 3. Type Scale

أقترح نثبت الـ scale ده كبداية:

| Token        | Size | Weight | Line Height | الاستخدام                   |
| ------------ | ---: | -----: | ----------: | --------------------------- |
| `display-lg` | 36px |    700 |        1.25 | العناوين الرئيسية جدًا      |
| `heading-xl` | 30px |    700 |        1.30 | Page Hero / Dashboard title |
| `heading-lg` | 24px |    700 |        1.35 | عناوين الأقسام الرئيسية     |
| `heading-md` | 20px |    600 |        1.40 | عناوين البطاقات/الأقسام     |
| `heading-sm` | 18px |    600 |        1.45 | Subsections                 |
| `body-lg`    | 16px |    400 |        1.70 | النص الأساسي                |
| `body-md`    | 14px |    400 |        1.65 | UI الأساسي                  |
| `body-sm`    | 13px |    400 |        1.60 | الجداول والمعلومات الثانوية |
| `caption`    | 12px |    400 |        1.50 | Metadata / hints            |

وده تقريبًا نفس الاتجاه اللي كنا مثبتينه، وأنا **لا أرى سببًا حاليًا لتغييره**.

---

# 4. الـ Weights

مش عايزين 8 أوزان في كل مكان.

نستخدم فقط:

### 400 — Regular

للنصوص.

### 500 — Medium

لـ:

* labels
* tabs
* بعض عناصر الـ navigation
* البيانات المهمة الصغيرة.

### 600 — Semibold

للعناوين الصغيرة والمتوسطة.

### 700 — Bold

للعناوين الرئيسية وKPI.

### 800 — Extra Bold

**نادر جدًا.**

يفضل استخدامه فقط عندما نحتاج hierarchy قوي جدًا، وليس كوزن عادي.

---

# 5. Arabic Letter Spacing

للعربية:

```text
letter-spacing: 0
```

ولا نحاول نعمل tracking اصطناعي للعربي.

خصوصًا في العناوين.

---

# 6. Latin

بالنسبة لـ Inter:

### Display

`-0.02em`

### Headings

`-0.01em`

### Body

`0`

وده يخلي الأرقام والعناوين الكبيرة أكثر تماسكًا بدون التأثير على القراءة.

---

# 7. KPI Typography

دي مهمة جدًا لسَنَد لأن عندنا Dashboard وDecision Support.

مثال:

**248**

يكون:

```text
Font: Inter
Weight: 700
Size: 30–36px
Line-height: 1.1–1.2
```

وتحته:

**طالبًا نشطًا**

```text
Font: Tajawal
Weight: 400–500
Size: 14px
```

يعني:

> **الرقم = Data**
> **الوصف = Human UI**

وده هيخلي الـ Dashboard أكثر احترافية.

---

# 8. الجداول

هنا لازم نكون حذرين.

جدول الطلاب هو أحد أهم أماكن اختبار شخصية سَنَد.

لا نريد:

❌ 16px لكل شيء
❌ عناوين ضخمة
❌ ألوان كثيرة
❌ Bold في كل خلية

الأساس:

### Table body

**13–14px / 400**

### Column header

**13px / 500–600**

### Primary information

**14px / 500**

### Secondary metadata

**12–13px / 400**

والـ hierarchy يأتي من:

**weight + spacing + surface + alignment**

وليس من تكبير الخط باستمرار.

---

# 9. Forms

في النماذج:

### Label

`14px / 500`

### Input

`14px / 400`

### Helper text

`12–13px / 400`

### Error

`12–13px / 500`

مثال:

**اسم الطالب**

`أحمد محمد`

`أدخل الاسم كما هو في السجل الرسمي`

ده يعطي إحساسًا مؤسسيًا هادئًا جدًا.

---

# 10. Navigation

الـ Sidebar عندنا RTL.

النص الأساسي:

**14px / 500**

العنصر المحدد لا يحتاج Font Size مختلف.

بدلًا من:

> 14 → 16 عند selection

نستخدم:

**Typography ثابتة + Color + Surface + Indicator**

وده مهم جدًا لأننا نريد hierarchy نظيف وليس UI صاخب.

---

# 11. Alignment

في العربية:

> **RTL هو الأصل.**

لكن الأرقام والبيانات الرقمية لها قواعدها الخاصة.

خصوصًا:

* الأرقام المالية
* النسب
* التواريخ
* IDs
* الأكواد
* أرقام الهاتف

لا نخلطها بصريًا داخل النص العربي.

---

# 12. أهم قرار Typography في سَنَد

أنا أقترح نضع قاعدة Design System صريحة:

> **Typography in Sanad should communicate hierarchy, not decoration.**

يعني الخط لا يحاول يكون "مميزًا" لذاته.

التميز يأتي من:

**الترتيب + المساحات + الـ hierarchy + اللون + المكونات.**

وده متوافق جدًا مع الشخصية التي بنيناها:

> **نظام حديث بروح رصينة.**

# A4 — Shape Language

هدفنا هنا أن تكون سَنَد **مؤسسية وهادئة**، وليست SaaS مليئة بالكروت المستديرة.

## Radius

أقترح تثبيت عائلة صغيرة:

| Token         | Value | الاستخدام                             |
| ------------- | ----: | ------------------------------------- |
| `radius-sm`   |   6px | عناصر صغيرة، badges، compact controls |
| `radius-md`   |   8px | Inputs / Buttons / Selects            |
| `radius-lg`   |  12px | Cards / Panels                        |
| `radius-xl`   |  16px | Dialogs / Large surfaces              |
| `radius-full` | 999px | Pills فقط                             |

### القاعدة

> **كلما كان العنصر وظيفيًا وصغيرًا، قلّ الـ radius.**

وبالتالي:

* Button → 8px
* Input → 8px
* Card → 12px
* Dialog → 16px
* Badge → حسب النوع، وليس تلقائيًا pill.

---

## Cards

الكارت في سَنَد **ليس الوحدة الأساسية لكل شيء**.

لا نريد:

> Card داخل Card داخل Card.

الكارت يستخدم عندما نحتاج فصلًا حقيقيًا بين مجموعتين من المعلومات.

**Card = Surface + Border + محتوى واضح**

والـ default لا يحتاج Shadow قوي.

---

## Buttons

الشكل:

* ارتفاع شائع: 36–40px
* Radius: 8px
* Font: 14px / 500
* Icon: 16–18px
* Padding أفقي: 14–16px

### Primary

واضح ومتماسك.

### Secondary

أهدأ، ولا ينافس Primary.

### Ghost

للأفعال الثانوية.

### Destructive

يظهر عند الحاجة فقط.

---

## Inputs

* Radius: 8px
* Border واضح لكن هادئ
* Height: 40px تقريبًا
* Label فوق الحقل
* Focus ring واضح
* Error لا يعتمد على الأحمر فقط؛ نستخدم icon/text أيضًا.

---

## Dialogs

`16px`

مع:

* Surface واضح
* Border subtle
* Shadow متوسط
* Header / Content / Actions hierarchy واضحة.

لا نريد Dialog يبدو كـ "floating glass".

---

## Tables

هنا نريد شخصية سَنَد أكثر من أي مكان آخر.

**لا نضع كل صف داخل Card.**

الجدول:

* Surface واحد.
* Header واضح.
* Borders خفيفة.
* Row hover subtle.
* Selected row له surface مختلف.
* كثافة معلومات جيدة.
* Radius خارجي 12px فقط إن كان الجدول داخل container.

الجدول يجب أن يشعر المستخدم:

> **هذه أداة إدارة حقيقية.**

---

## Badges

نستخدم pill فقط عندما يكون المعنى **status/tag**.

مثلاً:

`نشط`

`مكتمل`

`قيد المراجعة`

لكن لا نحول كل button أو control إلى pill.

---

## Menus

Radius:

**8px**

وليس 16px أو 20px.

Menu يجب أن يبدو كجزء من النظام، وليس floating widget.

---

# A5 — Elevation & Depth

هنا أريد تثبيت مبدأ مهم:

> **Depth في سَنَد يأتي أولًا من Surface hierarchy، ثم Border، ثم Shadow.**

وليس العكس.

## Elevation 0

Canvas / Page

```text
Shadow: none
Border: none
```

---

## Elevation 1

Surface أساسي:

```text
Border: subtle
Shadow: none أو شبه غير محسوس
```

يستخدم للـ Cards الأساسية.

---

## Elevation 2

عندما نحتاج فصلًا واضحًا:

```text
Border: subtle
Shadow: soft
```

مثل:

* Dropdown
* Popover
* بعض الـ Panels.

---

## Elevation 3

Floating elements:

* Dialog
* Menu مهم
* Command surface

Shadow أوضح، لكن بدون مبالغة.

---

## Elevation 4

للعناصر التي يجب أن تكون فوق كل شيء:

* Modal
* Critical overlay
* بعض الـ drawers.

وهذا سيكون **نادر الاستخدام**.

---

### Dark Mode

هنا القاعدة أهم:

> **لا نحاول تقليد Light Mode بالـ shadows.**

نستخدم:

**Surface contrast → Border → Shadow**

يعني مثلًا:

```text
Background
↓
Surface
↓
Elevated Surface
↓
Overlay
```

كل مستوى له فرق في الـ surface نفسه.

---

# B4 — Responsive & Accessibility

## 1. Breakpoints

مش هنخترع breakpoints خاصة بـSanad؛ نستخدم نظام Tailwind كأساس، ونحدد فقط **سلوك Sanad** عند الانتقال بينها.

| المستوى | العرض التقريبي | سلوك Sanad                              |
| ------- | -------------: | --------------------------------------- |
| Mobile  |      `< 640px` | Single column، Sidebar تتحول إلى drawer |
| Tablet  |   `640–1023px` | محتوى مرن، navigation مضغوطة            |
| Desktop |  `1024–1279px` | Sidebar + content                       |
| Wide    |     `≥ 1280px` | المساحة تستغل بشكل أفضل                 |

### قاعدة مهمة

**Responsive ≠ تصغير Desktop.**

مثلاً الـDashboard على Mobile قد يتحول من:

```text
KPI  KPI  KPI  KPI
```

إلى:

```text
KPI
KPI
KPI
KPI
```

لكن بعض البيانات قد تحتاج **horizontal scroll** بدل تدمير الجدول.

---

## 2. RTL

Sanad **RTL-first**.

```text
Sidebar → Right
Primary navigation → Right
Text alignment → Right
Tables → context-dependent
Numbers → remain visually stable
```

لكن لا نفترض أن كل شيء RTL بشكل أعمى.

مثلاً:

* الأرقام: لا نعكس ترتيبها.
* البريد الإلكتروني: LTR.
* URLs: LTR.
* الأكواد: LTR.
* بعض identifiers: LTR.

القاعدة:

> **RTL هو اتجاه الواجهة، وليس اتجاه كل محتوى داخلها.**

---

## 3. Density

نثبت:

> **Comfortable Dense**

يعني النظام يسمح بإدارة أعداد كبيرة من الطلاب والبيانات، لكن بدون الإحساس القديم للأنظمة الإدارية المكتظة.

خصوصًا:

* Tables → أكثر كثافة.
* Forms → متوسطة.
* Dashboard → أكثر تنفسًا.
* Mobile → أكبر لمسًا.

---

## 4. Touch Targets

العناصر التفاعلية الأساسية:

```text
Minimum practical target ≈ 40px
Preferred ≈ 44px
```

خصوصًا:

* Buttons
* Navigation
* Checkbox
* Switch
* Icon buttons

الأيقونة نفسها يمكن أن تكون 16–20px، لكن **منطقة الضغط أكبر**.

---

## 5. Accessibility

نلتزم مبدئيًا بـ:

* Contrast واضح.
* Focus ظاهر.
* Keyboard navigation.
* Labels حقيقية للـinputs.
* Error لا يعتمد على اللون فقط.
* Status لا يعتمد على اللون فقط.
* Motion محدود.
* احترام `prefers-reduced-motion`.

### مبدأ Sanad

> **Accessibility جزء من الوضوح، وليست طبقة إضافية بعد التصميم.**

مثلاً:

| Sanad                  | shadcn                   |
| ---------------------- | ------------------------ |
| `background`           | `--background`           |
| `foreground`           | `--foreground`           |
| `card`                 | `--card`                 |
| `card-foreground`      | `--card-foreground`      |
| `popover`              | `--popover`              |
| `popover-foreground`   | `--popover-foreground`   |
| `primary`              | `--primary`              |
| `primary-foreground`   | `--primary-foreground`   |
| `secondary`            | `--secondary`            |
| `secondary-foreground` | `--secondary-foreground` |
| `muted`                | `--muted`                |
| `muted-foreground`     | `--muted-foreground`     |
| `accent`               | `--accent`               |

| `ring`                 | `--ring`                 |

وبالتالي Components الموجودة أصلًا في shadcn تستفيد من Sanad مباشرة.

# 4. Dark / Light

نستخدم:

```text
:root
```

للـLight.

و:

```text
.dark
```

للـDark.

لكن **القيم لا تكون مجرد inversion**.

نظام C الذي اخترناه أصلًا يعطينا:

```text
Light Primary → #0A6C7E
Dark Primary  → #4FB3C4
```

وهكذا كل theme له hierarchy خاص به.

---

# 5. لا Token Explosion

دي قاعدة مهمة جدًا.

مش هنطلع بـ:

```text
--blue-50
--blue-100
--blue-200
...
```

ثم نستخدمهم في كل Component.

بدلًا من ذلك:

```text
primary
secondary
accent
muted
success
warning
error
info
```

والـcomponents تستهلك **intent**.

> **Token describes intent, not appearance.**

---

# 6. shadcn Components

الأصل:

**نستخدم الموجود ونعدله عند الحاجة.**

لا نعيد بناء:

* Button
* Input
* Dialog
* Dropdown
* Tabs
* Checkbox
* Select
* Table

من الصفر لمجرد أن Sanad له هوية.

لكن عندما تظهر حاجة حقيقية:

```text
shadcn component
      ↓
Sanad customization
```

وليس:

```text
shadcn component
      ↓
discard
      ↓
completely new system
```

---

# B6 — Sanad Component Rules

الآن نضع **قواعد المكونات** التي ستمنع التصميم من الانحراف أثناء بناء الشاشات.

## 1. Button

### Primary

للإجراء الرئيسي.

### Secondary

للإجراءات المهمة لكن الأقل أولوية.

### Outline

لإجراء ثانوي واضح.

### Ghost

للإجراءات الخفيفة.

### Destructive

للأفعال الخطرة.

قاعدة:

> **صفحة واحدة لا تحتاج 5 Primary actions.**

يجب أن يكون هناك hierarchy واضح.

---

# 2. Input

```text
Label
↓
Input
↓
Helper / Error
```

المواصفات:

* Radius 8px.
* Height تقريبًا 40px.
* Label واضح.
* Focus واضح.
* Error لا يعتمد على الأحمر وحده.
* Placeholder ليس بديلًا عن Label.

---

# 3. Cards

Card ليست default container.

نستخدمها عندما يوجد:

> **Grouping with meaning**

مثلاً:

```text
Student Summary
```

مناسب.

لكن:

```text
كل عنصر في الصفحة داخل Card
```

مرفوض.

---

# 4. Tables

الجدول عنصر أساسي في Sanad.

### قواعده

* Header واضح.
* Borders خفيفة.
* Row height مريحة.
* Hover subtle.
* Selected واضح.
* Actions في مكان ثابت.
* لا نحول كل row إلى Card.

وعلى Mobile:

إما:

```text
Horizontal scroll
```

أو:

```text
Responsive alternate presentation
```

حسب طبيعة البيانات.

---

# 5. Dialog

```text
radius-xl → 16px
```

Hierarchy:

```text
Title
↓
Description / Context
↓
Content
↓
Actions
```

ولا نستخدم:

* Glassmorphism.
* Blur مبالغ.
* Shadows ضخمة.

---

# 6. Badges

`Badge` يستخدم عندما تكون المعلومة **status/tag/category**.

مثلاً:

```text
نشط
متوقف
مكتمل
متأخر
```

لكن لا نحول كل button إلى pill.

---

# 7. Navigation

Sidebar:

* RTL.
* Right side.
* Icon + label.
* Active state واضح.
* لا نعتمد على تغيير حجم الخط.
* Groups واضحة.
* لا نستخدم الألوان بكثرة.

والـactive item يعتمد على:

```text
surface
+
foreground
+
indicator
```

وليس لونًا صارخًا فقط.

---

# 8. Forms

Form Sanad يجب أن تكون:

> **واضحة قبل أن تكون جميلة.**

القواعد:

```text
Section
↓
Field
↓
Helper
↓
Validation
```

والـsections تستخدم spacing لتوضيح العلاقة، وليس Card لكل مجموعة.

---

# 9. Feedback

كل Feedback يستخدم نفس اللغة:

```text
Success → نجاح
Warning → يحتاج انتباه
Error → فشل / مشكلة
Info → معلومة
```

وكل حالة تستخدم:

```text
Color
+
Icon
+
Text/context
```

عندما يكون ذلك مناسبًا.

---

# 10. Motion

Motion في Sanad:

> **Calm + Functional**

نستخدمه في:

* Opening/closing.
* State transition.
* Loading.
* Navigation.
* Feedback.

ولا نستخدمه للزخرفة.

الهدف:

> يشعر المستخدم أن النظام **مستجيب**، وليس أن النظام **يستعرض نفسه**.

   عشان أعرف إعدادات shadcn عندك والـaliases والـstyling configuration.

   **لو موجود**.

4. **ملفات الـtheme إن كانت منفصلة**
   مثل:

   * `theme.ts`
   * `theme.css`
   * `tokens.css`
   * أو أي ملف عندك مسؤول عن الألوان/الثيم.

### مهم جدًا لـ C3

5. **ملف الـSidebar الأساسي**
   غالبًا شيء مثل:


   أو الملف المقابل عندك.

6. **أي Layout أساسي**
   خصوصًا:

   ```text

   ```

   أو الـlayout المسؤول عن RTL والـfonts.

### مفيد جدًا لـ C4

7. **أي Components خاصة بالـCharts موجودة حاليًا**
   مثل:

   ```text

   ```

   أو أي chart wrapper تستخدمه.

8. **`package.json`**

   ده مهم عشان أعرف بالضبط:

   * نسخة Next.js

   * shadcn/Radix
   * lucide
   * chart library
   * وأي dependencies مؤثرة.

# Sanad Design Philosophy

Sanad ليس مجرد Quran app ولا مجرد SaaS dashboard.

هو:

> نظام حديث بروح رصينة.

الشخصية:

* Reliable: 10/10
* Clear: 10/10
* Calm: 9/10
* Formal: 8/10
* Modern: 7/10
* Technical: 7/10
* Human: 6/10
* Luxury: 4/10
* Color Boldness: 4/10
* Ornamentation: 2/10

Design compass:

> **Depth + Restraint + Clarity**

الهوية القرآنية لا تأتي من الزخارف الإسلامية أو الأقواس أو الذهب أو صور المساجد.

والهوية التقنية لا تأتي من gradients أو glassmorphism أو SaaS clichés.

المطلوب:

> **روح قرآنية + هندسة تقنية**

---

# Anti-Cliché Rules

تجنب في الـfoundation:

* Purple AI gradients
* Mesh gradients
* Glassmorphism
* Excessive rounded cards
* Floating blobs
* Rainbow dashboards
* Neon colors
* Generic startup SaaS appearance
* Stock Islamic imagery
* Excessive Islamic ornamentation
* Gold فقط لأنه "ديني"
* Green فقط لأنه "قرآن"

لا تضف شيئًا بصريًا إلا إذا كان له سبب وظيفي أو هوياتي واضح.

# Elevation System

Elevation ليست shadow فقط.

أنشئ foundation لـ:

```text
elevation-0
elevation-1
elevation-2
elevation-3
elevation-4
```

المفهوم:

```text
E0
Canvas
No border
No shadow

E1
Basic surface
Subtle border
Minimal/no shadow

E2
Raised/floating
Subtle border
Soft shadow

E3
Dialog/floating
Stronger border
Medium shadow

E4
Overlay/modal
Strongest controlled elevation
```

في Dark Mode:

> Surface contrast + Border أهم من Shadow.

لا تستخدم shadows ثقيلة لمحاولة إظهار العمق.

# Radius

Foundation:

```text
radius-sm    6px
radius-md    8px
radius-lg    12px
radius-xl    16px
radius-full  999px
```

Semantic usage:

```text
sm   small controls
md   inputs/buttons
lg   cards/panels
xl   dialogs/large surfaces
full badges/pills فقط عندما يكون لها معنى
```

لا تجعل كل component rounded لمجرد الشكل.

# Spacing

لا تنشئ spacing system منفصل عن Tailwind.

استخدم spacing system الموجود في Tailwind، لكن اجعل usage consistent.

اللغة العامة:

```text
4 / 6 / 8
12 / 16 / 20 / 24
32 / 40 / 48 / 64
```

لا تنشئ عشرات tokens جديدة للـspacing بدون حاجة.

# Layout Foundation

Sanad:

> RTL-first

Desktop:

```text
Sidebar → Right
Main Content → Left
```

Page padding:

```text
Desktop → 32px
Tablet  → 24px
Mobile  → 16px
```

Responsive من البداية.

لا تبني desktop ثم تحاول إصلاح mobile لاحقًا.

---

# Responsive Philosophy

لا نريد مجرد تصغير desktop.

Mobile يجب أن يكون responsive adaptation حقيقي.

أمثلة:

* Dashboard cards يمكن أن تصبح single-column.
* Tables يمكن أن تستخدم horizontal scrolling عند الحاجة.
* Navigation تتحول إلى drawer/mobile pattern.
* Touch targets تصبح مناسبة للمس.

لا تغير محتوى أو UX بدون سبب.

# IMPORTANT — Tailwind Utility Strategy

نريد الاستفادة من Tailwind، لكن لا نريد تكرار نفس التصميم في كل شاشة.

إذا كانت قيمة أو pattern:

* متكررًا
* semantic
* جزءًا من هوية Sanad
* أو يحتاج consistency

فالأفضل تعريفه مرة واحدة في الـtheme/style layer أو reusable utility/component مناسب.

مثلاً:

بدل تكرار styling طويل لنفس container في عشرات الصفحات، أنشئ abstraction مناسب مثل:

```text
container / page-container
```

أو utility semantic مناسبة.

لكن:

**لا تحول كل Tailwind utility إلى custom class.**

Tailwind utilities البسيطة ما زالت مسموحة.

المطلوب هو منع:

```text
hardcoded brand values
```

ومنـع تكرار نفس combination من utilities في كل مكان.

---

# VERY IMPORTANT — No Hardcoded Brand Values

بعد إعداد الـtokens، لا تستخدم في application code:

```text
bg-[#0A6C7E]
text-[#0A6C7E]
border-[#...]
shadow-[...]
```

إذا كان اللون أو القيمة جزءًا من Design System، استخدم semantic token.

مثال:

```text
bg-primary
text-primary-foreground
border-border
bg-muted
text-muted-foreground
```

ولـSanad custom tokens استخدم الـsemantic names المناسبة.

الهدف:

> تغيير الهوية لاحقًا يجب أن يكون ممكنًا من طبقة الـtokens، وليس من مئات الملفات.

# Final instruction

نفّذ الـFoundation بعناية، وراجع الملفات الحالية قبل تعديلها.

لا تحذف functionality موجودة.

لا تغير behavior الموجود إلا إذا كان ضروريًا للـtheme/foundation.

لا تضف dependencies جديدة إلا إذا كانت ضرورية فعلًا.

بعد التنفيذ، أعطني تقريرًا مختصرًا يوضح:

1. الملفات التي تم تعديلها.
2. الـtokens التي تمت إضافتها.
3. الـtokens التي تمت إعادة mapping لها.
4. أي utilities/foundations جديدة.
5. أي قرارات اضطررت لاتخاذها بسبب بنية المشروع.
6. أي شيء لم تستطع تنفيذه بأمان وتحتاج مني مراجعته.

ثم **توقف ولا تبدأ Component Review**.
