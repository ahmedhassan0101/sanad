# أين نحن وإلى أين

## كيف تقرأ هذا الملف
- جدول الحالة أولًا: ماذا يعمل فعلًا وماذا لا.
- ثم مشاكل رأيتها في الكود (بدون إصلاح).
- ثم الخطوات التالية بالترتيب، وسؤال لك قبل كل خطوة.

## جدول الحالة
| الميزة | الحالة | الدليل |
|---|---|---|
| تسجيل بإيميل/باسورد + دخول | يعمل | `registerAction`/`loginAction` + اختبار دخاني سابق |
| دخول Google | يعمل (بالمفاتيح) | زر مشروط في `login/page.tsx` |
| تأكيد الإيميل | يعمل (رابط في الـ logs) | `verifyEmailToken` + صفحة verify |
| استعادة الباسورد | تعمل (رابط في الـ logs) | `requestPasswordReset`/`resetPassword` |
| إرسال إيميل حقيقي | غير مبني | `sendAuthLink` تطبع فقط |
| تسجيل الخروج (زر) | غير مبني | لا زر ولا مستدعٍ لـ `signOut` |
| إنشاء مركز (transaction) | يعمل | `createCenter` + حد 3 + شرط التفعيل |
| الانضمام بكود | يعمل | `consumeInvite` (ذري + إعادة فحص) |
| إنشاء الدعوات من الواجهة | غير مبني | `createInvite` بلا صفحة |
| إدارة الفريق/الأدوار | غير مبنية | `guardAdminChange` بلا واجهة |
| الفروع (عرض) | يعمل جزئيًا | الداشبورد يعرضها؛ لا إنشاء فرع ثانٍ من الواجهة |
| البرامج (اختيار عند الإنشاء) | يعمل | لا إدارة لاحقة (تفعيل/تعطيل) |
| صفحة المنصة (أدمن عام) | تعمل | `platform/page.tsx` + seed |
| بوابة ولي الأمر | غير مبنية | زر معطل فقط |
| الطلاب/المجموعات/الحضور | غير مبنية | كارت «قريبًا» فقط |
| UI foundation (شادن + فورمات + سمة + خطوط) | يعمل | كل الصفحات بالبطاقات + `/ui-demo` |
| توكنات Sanad | تعمل | `globals.css` + `docs/sanad-tokens.md` |
| الاختبارات الآلية | تعمل (19 ناجحة) | `npm run test` |

## مشاكل وديون رأيتها (بدون إصلاح)
1. `sessionVersion` يُرفع عند تغيير الباسورد لكن لا شيء يقارنه — «الخروج من كل الأجهزة» غير مفعّل فعليًا، والـ JWT لا يحمله أصلًا.
2. لا زر خروج في أي صفحة — الجلسة تبقى حتى انتهائها.
3. تحقق `branchIds` في الـ schema يعمل عند الإنشاء فقط وليس التحديث المباشر — الأمان الحالي يعتمد على مرور كل كتابة عبر الـ services.
4. `guardAdminChange` يعدّ الأدمنز خارج transaction — سباق نظري موثق في الكود (`adminsVersion` موجود للحل لاحقًا).
5. `getPlatformStats` تقرأ كل المراكز دفعة واحدة — تكفي الآن وتحتاج ترقيم صفحات لاحقًا.
6. رابط التحقق/الاستعادة يُطبع في الـ logs — أي وصول للـ terminal يعني اختراق حسابات (مقبول للتطوير فقط).

## الخطوات التالية المقترحة
1. **زر الخروج + تفعيل `sessionVersion`**: الهدف جلسات آمنة. يُبنى زر في الداشبورد ينادي `signOut`، وتُضاف مقارنة النسخة في `getSessionContext`. البدء من `dashboard/page.tsx` و`session-context.ts`. سؤال: هل الخروج من جهاز واحد أم كل الأجهزة؟
2. **إنشاء الدعوات من الواجهة**: الهدف إدخال المعلمين فعليًا. تُبنى صفحة للمالك/المشرف تعرض `createInvite` وتُظهر الكود مرة واحدة. البدء من `services/invites.ts` وصفحة جديدة. سؤال: من يرى الأكواد النشطة ويلغيها؟
3. **إدارة الفريق**: الهدف تفعيل `guardAdminChange`. صفحة أعضاء المركز (تغيير دور/تعطيل). البدء من `services/memberships.ts`. سؤال: هل المعلم يرى قائمة زملائه؟
4. **الطلاب والمجموعات**: الهدف أول كيان تعليمي. جداول + صفحات جديدة بالنطاق نفسه. سؤال: هل الطالب يُسجَّل برقم هاتف ولي الأمر من البداية؟

## أسئلة قبل الخطوة التالية
- أي خطوة من الأربع أولًا؟
- هل أبني واجهة إنشاء الدعوات قبل إدارة الفريق أم معًا؟

# المسارات (Flows)

## كيف تقرأ هذا الملف
- كل مسار رسمة نصية من الضغطة حتى الداتابيز والعودة.
- تحت كل رسمة: الملف والدالة الفعليان لكل خطوة، وما يحدث عند الخطأ.
- الأسماء حرفية كما في الكود.

## 1) Auth Flow (التسجيل والدخول)

### 1-أ) حساب جديد بإيميل وباسورد
```
زر «إنشاء الحساب»
  → الفورم يتحقق محليًا (registerSchema)
  → registerAction (register/actions.ts)
  → registerAccount (services/auth-accounts.ts): إيميل مكرر؟ اسم/باسورد قصير؟
  → User.create + VerificationToken.create (بصمة الرابط لا نصه)
  → sendAuthLink: يطبع الرابط في الـ logs فقط (الإرسال الحقيقي لسه مش مبني)
  → signIn("credentials") دخول تلقائي → تحويل /onboarding
```
- عند الخطأ: إيميل مكرر ← رسالة «هذا البريد مسجل بالفعل». حقول ناقصة ← «تحقق من الحقول».

### 1-ب) الدخول بإيميل وباسورد
```
زر «دخول»
  → loginAction (login/actions.ts) يتحقق من loginSchema
  → signIn("credentials") (src/lib/auth/config.ts)
  → authorize → verifyCredentials: يبحث بالإيميل + يقارن البصمة + يرفض غير active
  → نجاح: JWT يُختم ويُحفظ في كوكي. فشل: رسالة «بيانات الدخول غير صحيحة أو الحساب موقوف»
```
- الـ JWT فيه `userId` فقط (سطر `token.userId` في callback الـ `jwt`). لا أدوار ولا مركز فيه.
- الـ session تُبنى منه عند كل قراءة (`session.user.id`) — الملف `src/lib/auth/config.ts`.

### 1-ج) الدخول بـ Google
```
زر «الدخول بـ Google» (يظهر فقط لو GOOGLE_CLIENT_ID موجود)
  → googleAction في login/page.tsx → signIn("google")
  → callback الـ signIn ينادي ensureGoogleUser: موجود؟ يرفض الموقوف ويثبّت التفعيل. جديد؟ ينشئه مفعّلًا
  → تحويل /onboarding
```

### 1-د) تأكيد الإيميل (مبني ويعمل)
```
الرابط /verify?email&token (من الـ logs)
  → verify/page.tsx تنادي verifyEmailToken
  → تطابق البصمة + عدم الانتهاء → User.emailVerifiedAt + حذف التوكن لمرة واحدة
  → «تم تفعيل بريدك» بزر إكمال، أو «الرابط غير صالح»
```
- التفعيل **شرط** إنشاء مركز (`createCenter` ترفض غير المفعّل).

### 1-هـ) نسيان الباسورد (مبني ويعمل)
```
forgot → forgotAction → requestPasswordReset: لو الحساب موجود ينشئ توكن ساعتين ويطبع الرابط (صمت تام لو غير موجود)
  → reset?email&token → resetAction → resetPassword: يبدّل البصمة + يرفع sessionVersion + يحذف التوكن → تحويل /login
```
- تحذير: رفع `sessionVersion` مكتوب لكن **لا شيء يقرأه** — الخروج من كل الأجهزة لسه مش مفعّل فعليًا (انظر STATUS_AND_NEXT).

### تسجيل الخروج (لسه مش مبني)
لا يوجد زر خروج في أي صفحة. الدالة `signOut` مُصدَّرة من الإعداد لكن بلا مستدعٍ.

## 2) User Flow (رحلة المستخدم)
```
/ → register (حساب) → /onboarding
  → الكارت 1 «إنشاء مركز جديد»: بيانات + برامج (واحد على الأقل + مخصص اختياري)
      → createCenterAction → createCenter → كوكي active_org → /dashboard
  → الكارت 2 «عندي كود دعوة»: كود من مشرف
      → enterCodeAction → consumeInvite → كوكي active_org → /dashboard
  → الكارت 3 «متابعة طفلي»: زر معطل (قريبًا) — لسه مش مبني
  → لو له عضويات: أزرار «دخول <اسم المركز>» تثبت الكوكي عبر setActiveOrg
/dashboard: اسم المركز + الدور + الفروع (تظهر فقط لو أكثر من فرع) + البرامج + كارت «قريبًا»
```
- إنشاء مركز بإيميل غير مفعّل ← رسالة «فعّل بريدك أولًا».
- أكثر من 3 مراكز لنفس المنشئ ← رفض `FORBIDDEN`.

## 3) API/Data Flow (مسار طلب كامل)
```
مثال: فتح /dashboard
صفحة (app/dashboard/page.tsx)
  → viewer() (services/viewer.ts): يقرأ الجلسة (auth) وكوكي active_org
  → getSessionContext(userId, activeOrgId) (services/session-context.ts):
     يقرأ User (الحالة؟ أدمن عام؟) ثم Membership (فعالة؟) ويبني {orgId, role, branchScope}
  → getDashboard(ctx) (services/screens.ts):
     التحقق zod كان في الـ action (للقراءة: لا مدخلات)
     الصلاحيات: kind必须为 member وإلا تحويل (في الصفحة نفسها)
     العزل: Org.findOne({_id, ...}) ضمنيًا + Branch.find(scopedFilter(ctx, "_id"))
  → الرد: كائن بيانات عادي {orgName, role, branches, programs}
     (ملاحظة: شكل Result الموحد معرّف لكن الأكشنات ترد {ok, message} مباشرة — انظر قسم غير المستخدم)
```
- القاعدة: `orgId` يأتي من السياق السيرفري دائمًا، والعميل لا يرسله أبدًا (الكوكي مجرد مؤشر يُتحقق منه).
- أي `findById` مباشر ممنوع بموجب قاعدة ESLint (الـ models لا تُستورد إلا في services/scripts/tests).

## 4) Context Flow (حالات السياق)
```
getSessionContext(userId, activeOrgId):
  userId فارغ/تالف → خطأ UNAUTHENTICATED (الصفحة تحوّل إلى /login)
  المستخدم غير موجود أو غير active → UNAUTHENTICATED
  isPlatformAdmin → {kind: "platform"} (يُقبل فقط في /platform، وغيره يُحوَّل)
  بلا active_org صالح → {kind: "onboarding"} (صفحات الداشبورد تحوّل إلى /onboarding)
  بلا عضوية فعالة في المركز → خطأ FORBIDDEN
  عضوية فعالة → {kind: "member", orgId, role, branchScope}
     الدور center_admin ← نطاق all (كل الفروع)
     غيره ← نطاق list (فروع العضوية فقط)
```

## 5) Create Org Flow (إنشاء مركز بالتفصيل)
```
createCenterAction (تحقق createCenterSchema + تحويل المخصص إلى custom:...)
  → createCenter (services/orgs.ts):
     1. تحقق داخلي ثانٍ + شرط الإيميل المفعّل + عد المراكز (3 كحد أقصى)
     2. transaction واحدة (mongoose.startSession + withTransaction):
        - Org.create (الاسم/التواصل/العنوان/createdByUserId)
        - Branch.create (نفس المركز، الاسم ثابت «الفرع الرئيسي»)
        - Membership.create (المنشئ center_admin بلا فروع)
        - OrgProgram.create (صف لكل برنامج مختار)
     3. عند أي فشل: الـ transaction تلغي الكل، والأكشن يرد رسالة عربية
  → كوكي active_org = المركز الجديد → تحويل /dashboard
```
- عند الخطأ: رسالة الخدمة تُعرض كما هي بعد حذف بادئة `VALIDATION:`/`FORBIDDEN:`.

## شجرة المجلدات
- `src/app/`: الصفحات التي يفتحها المستخدم في المتصفح. كل مجلد باسمه = عنوان في الموقع.
- `src/components/ui/`: قطع جاهزة من مكتبة shadcn (زر، كارت، حقل إدخال). مولّدة آليًا — لا تعدلها بيدك.
- `src/components/form/`: حقول فورمات جاهزة من صنع المشروع، كل حقل يُستخدم بسطر واحد.
- `src/components/`: مكونات عامة من صنع المشروع (مبدل السمة...).
- `src/lib/`: دوال صغيرة نقية. كلمة نقية تعني لا تفتح الداتابيز بنفسها.
- `src/db/`: شكل الجداول (models) وطريقة الاتصال بالداتابيز.
- `services/`: العقل. أي قراءة أو كتابة في الداتابيز تتم من هنا فقط، وبعده تُمنع في الصفحات (قاعدة ESLint).
- `src/validators/`: قواعد التحقق (zod) المشتركة بين المتصفح والسيرفر.
- `scripts/`: أوامر تُشغَّل من سطر الأوامر (terminal) وليست صفحات.
- `tests/`: اختبارات آلية تتأكد أن العزل بين المراكز يعمل.
- `docs/`: هذا التوثيق وملفات مرجعية أخرى.
- `middleware.ts` (جذر): بوابة خفيفة تتحقق هل الزائر مسجل دخول أم لا.

## طبقة app/ (الصفحات)
كل صفحة ملف اسمه `page.tsx`. ملف `form.tsx` يعني فورم تفاعلي (Client Component — يعمل في المتصفح). ملف `actions.ts` يعني دوال سيرفر (Server Action — تعمل على السيرفر وتُستدعى من الفورم).

- `src/app/page.tsx`: صفحة البداية. تعرض كارت «سَنَد» مع زري الدخول والحساب. لو مسجل دخول تحوله إلى `/onboarding`. لا تنادي services.
- `src/app/layout.tsx`: الغلاف العام لكل الصفحات (الخطوط، الاتجاه RTL، السمة، التنبيهات). لا منطق فيه.
- `src/app/loading.tsx`: شاشة تحميل (Skeleton — مستطيلات رمادية متحركة) تظهر أثناء فتح أي صفحة.
- `src/app/not-found.tsx`: صفحة 404 بزر عودة للبداية.
- `src/app/login/page.tsx`: كارت الدخول + زر Google (يظهر فقط لو مفاتيح Google موجودة). فيها `googleAction` تنادي `signIn("google")` من `src/lib/auth/config.ts`.
- `src/app/login/form.tsx`: فورم الدخول. الدالة `LoginForm` تنادي `loginAction` من `./actions`، وعند الفشل تعرض الرسالة بـ `FormAlert` وتنبيه `toast`.
- `src/app/login/actions.ts`: الدالة `loginAction(values)` تتحقق من `loginSchema` ثم تنادي `signIn("credentials")` من `src/lib/auth/config.ts`. عند النجاح تحول إلى `/onboarding`.
- `src/app/register/page.tsx` + `form.tsx` (الدالة `RegisterForm`): نفس نمط الدخول.
- `src/app/register/actions.ts`: الدالة `registerAction(values)` تتحقق من `registerSchema` ثم تنادي `registerAccount` من `services/auth-accounts.ts` (الخطأ `TAKEN` يعني الإيميل مسجل)، ثم دخول تلقائي ثم تحويل إلى `/onboarding`.
- `src/app/forgot/page.tsx` + `form.tsx` (الدالة `ForgotForm`): تطلب الإيميل فقط.
- `src/app/forgot/actions.ts`: الدالة `forgotAction(values)` تنادي `requestPasswordReset` من `services/auth-accounts.ts` وترد دائمًا بنجاح حتى لا تكشف وجود الحسابات.
- `src/app/reset/page.tsx` + `form.tsx` (الدالة `ResetForm` تستقبل `email` و`token`): كلمة مرور جديدة.
- `src/app/reset/actions.ts`: الدالة `resetAction(email, token, values)` تنادي `resetPassword` من `services/auth-accounts.ts`، وعند النجاح تحول إلى `/login`.
- `src/app/verify/page.tsx`: صفحة تفعيل الإيميل من الرابط. تنادي `verifyEmailToken` من `services/auth-accounts.ts` وتعرض نجاحًا أو فشلًا مع زر مناسب.
- `src/app/onboarding/page.tsx`: شاشة البداية بعد الدخول. تنادي `auth()` ثم `listMyMemberships` من `services/org-selection.ts`. تعرض أزرار «دخول» لكل عضوية (كل زر فورم صغير ينادي `setActiveOrg`) + 3 كروت: إنشاء مركز / عندي كود / متابعة طفلي (معطل).

- `src/app/onboarding/create-center/form.tsx`: الدالة `CreateCenterForm` تستخدم `FormCheckboxes` للبرامج من `PROGRAM_CATALOG` في `src/lib/programs.ts` + حقل برنامج مخصص، وتنادي `createCenterAction`.

## طبقة services/
- `services/auth-accounts.ts`: `registerAccount` (إنشاء + رابط تفعيل، الخطأ `TAKEN` للإيميل المكرر) ← يناديها `registerAction`. `verifyEmailToken` ← صفحة verify. `requestPasswordReset` (صامتة لو الحساب غير موجود) ← `forgotAction`. `resetPassword` (ترفع `sessionVersion`) ← `resetAction`. `verifyCredentials` ← إعداد Auth.js. `ensureGoogleUser` ← إعداد Auth.js عند دخول Google.
- `services/session-context.ts`: `getSessionContext(userId, activeOrgId)` تبني السياق من الداتابيز في كل طلب: بلا user ← `UNAUTHENTICATED`، أدمن عام ← `platform`، بلا مركز ← `onboarding`، بلا عضوية فعالة ← `FORBIDDEN`، وإلا `member` بالنطاق من الدور. تنادي `User` و`Membership`. يناديها `viewer`.
- `services/viewer.ts`: `viewer()` تقرأ الجلسة (`auth`) وكوكي `active_org` ثم تنادي `getSessionContext`. تناديها صفحات dashboard وplatform.
- `services/org-selection.ts`: `listMyMemberships(userId)` (عضوياتي الفعالة مع أسماء المراكز) ← صفحة onboarding. `activateOrg(userId, orgId)` (تتحقق من عضوية فعالة) ← أكشن `setActiveOrg`.
- `services/orgs.ts`: `createCenter(userId, raw)` تتحقق داخليًا بـ schema خاص، تشترط إيميلًا مفعّلًا و3 مراكز كحد أقصى، ثم transaction واحدة تكتب Org + فرع «الفرع الرئيسي» + عضوية مالك + البرامج. يناديها أكشن إنشاء المركز.
- `services/invites.ts`: `createInvite` (إنشاء كود بحد 20 نشطة، بلا مستدعٍ من الواجهة حاليًا) و`consumeInvite` (استهلاك ذري بشرط واحد ثم إعادة فحص صلاحية الداعي والفرع، ثم إنشاء عضوية أو إعادة تفعيل معطلة). تنادي `assertMembershipShape` و`assertBranchesInOrg`. ينادي `consumeInvite` أكشن إدخال الكود.
- `services/memberships.ts`: `assertMembershipShape` (الفروع إجبارية للأدوار المحدودة) و`assertBranchesInOrg` (الفروع داخل نفس المركز) و`guardAdminChange` (حماية المنشئ وآخر أدمن — مع ملاحظة سباق مكتوبة في الكود) و`assertRankAllows`. تُستخدم في `invites.ts` والاختبارات فقط حاليًا.
- `services/screens.ts`: `getDashboard(ctx)` (اسم المركز + الفروع بالنطاق + البرامج) ← الداشبورد. `getPlatformStats()` (أرقام كل المراكز) ← صفحة المنصة.
- `services/branches-read.ts`: `listBranches(ctx)` خدمة صغيرة للاختبار فقط — لا تستخدمها الصفحات.

## طبقة db/models/
كلها تعريف شكل الجدول فقط (Mongoose Schema). الجداول الفعلية في MongoDB بأسماء جمع lowercase (users, orgs...).
- `User.ts`: الهوية (اسم/إيميل فريد/صورة/باسورد مخفي `select:false`/حالة/أدمن عام/`sessionVersion`). تُقرأ من كل خدمات الحسابات والسياق.
- `Org.ts`: المركز + `adminsVersion` (مخصص لمنع السباق لاحقًا) + منشئ المركز.
- `Branch.ts`: الفرع (اسم فريد داخل المركز + حالة). فهرس `{orgId, name}` فريد.
- `Membership.ts`: العضوية (مستخدم + مركز + دور + فروع + حالة). فهرس `{userId, orgId}` فريد. تحقق الفروع يعمل عند الإنشاء فقط وليس عند التحديث المباشر.
- `Invite.ts`: الدعوة (كود مُبصَّم لا يُخزَّن نصًا + انتهاء + استخدام/إلغاء + `purgeAt` للحذف بعد 30 يومًا). الفرع إجباري لغير المالك.
- `OrgProgram.ts`: برامج المركز المفعلة. فهرس `{orgId, programKey}` فريد.
- `VerificationToken.ts`: روابط التفعيل والاستعادة لمرة واحدة (تُحذف بانتهائها).
- `AuditLog.ts`: سجل الأحداث (يُحذف بعد 180 يومًا). لا كتابة فيه من أي service حاليًا.
- `RateLimit.ts`: عدّادات الحماية (تُحذف بعد 24 ساعة). لا استخدام لها حاليًا.
- `src/db/connection.ts`: `connectDB(uri?)` اتصال واحد مخزن يُعاد استخدامه، والفهارس تُبنى تلقائيًا خارج الإنتاج.

## طبقة validators/

# الشاشات والصفحات

## كيف تقرأ هذا الملف
- صفحة لكل مسار موجود فعلًا في `src/app/`.
- لكل صفحة: ماذا ترى، وماذا تفعل، وبياناتها من أين، وأين تذهب بعد كل إجراء.
- آخر قسم للنوافص.

## `/` — البداية (`app/page.tsx`)
- ترى: كارت «سَنَد» + زري الدخول والحساب.
- البيانات: الجلسة فقط. المسجل يُحوَّل تلقائيًا إلى `/onboarding`.
- لا أفعال هنا.

## `/login` — الدخول (`app/login/*`)
- ترى: زر Google (مشروط بالمفاتيح) + حقلا الإيميل والباسورد (إظهار/إخفاء) + رابطا الحساب والنسيان.
- الفعل: دخول ← نجاح يحول إلى `/onboarding`، فشل يعرض رسالة حمراء + تنبيهًا.
- المكونات: `Card` و`LoginForm` (`FormInput` + `FormSubmitButton`).

## `/register` — حساب جديد (`app/register/*`)
- ترى: الاسم + الإيميل + الباسورد (مع تلميح 8 أحرف).
- الفعل: إنشاء ← إنشاء الحساب + دخول تلقائي ← `/onboarding`. الإيميل المكرر رسالته الخاصة.
- ملاحظة: رابط التفعيل يُطبع في الـ logs — افتح الـ terminal لتنسخه.

## `/forgot` و`/reset` — الاستعادة (`app/forgot/*`, `app/reset/*`)
- `/forgot`: إيميل واحد. الرد دائمًا «إن وُجد الحساب ستصلك رسالة» حتى لو لا حساب.
- `/reset`: يفتح فقط برابط صحيح (`email`+`token`). حفظ ناجح ← `/login`. رابط منتهي ← رسالة تطلب رابطًا جديدًا.

## `/verify` — التفعيل (`app/verify/page.tsx`)
- لا فورم فيها: تعمل تلقائيًا من الرابط وتعرض نجاحًا بزر «أكمل» أو فشلًا بزر عودة.

## `/onboarding` — البداية (`app/onboarding/*`)
- ترى: ترحيبًا بالاسم + أزرار «دخول» لكل عضوية فعالة (تثبت الكوكي عبر `setActiveOrg` ثم `/dashboard`) + 3 كروت.
- الكروت: إنشاء مركز (يعمل) / كود دعوة (يعمل) / متابعة طفلي (معطل).

## `/onboarding/create-center` — إنشاء مركز (`app/onboarding/create-center/*`)
- ترى: الاسم + التواصل + العنوان + برامج (checkboxes من الكتالوج) + مخصص + زر إنشاء.
- الفعل: نجاح ← `/dashboard` (الكوكي يُثبَّت تلقائيًا). فشل ← رسالة (منها: فعّل بريدك، الحد 3 مراكز).
- البيانات الخارجة: مركز + فرع رئيسي + عضوية مالك + برامج (transaction واحدة).

## `/onboarding/enter-code` — الكود (`app/onboarding/enter-code/*`)
- ترى: حقل كود واحد + زر انضمام.
- الفعل: كود صحيح ← عضوية بالدور المحدد في الدعوة ← `/dashboard`. كود خاطئ/منتهي/مستخدم ← رسالة. العضو الحالي ← «أنت عضو بالفعل».

## `/dashboard` — اللوحة (`app/dashboard/page.tsx`)
- ترى: اسم المركز + دورك + مبدل السمة + الفروع (فقط لو أكثر من فرع) + البرامج + كارت «قريبًا» + زر تبديل المركز.
- البيانات: من `getDashboard` بالنطاق الخاص بك (المعلم يرى فروعه فقط).
- غير العضو يُحوَّل إلى `/onboarding`.

## `/platform` — المنصة (`app/platform/page.tsx`)
- ترى: بطاقة لكل مركز (اسم/فروع/أعضاء/برامج/تواصل) — أرقام فقط.
- للأدمن العام فقط (يُزرع بالـ seed). غيره يُحوَّل إلى `/onboarding`.

## `/ui-demo` — المعرض (`app/ui-demo/*`)
- ترى: كل الأزرار والحالات وحقلي معطل/قراءة فقط وفورم تجريبي كامل (إنشاء وتعديل) وأزرار toast وهيكل تحميل ومبدل السمة.
- للتطوير فقط: في الإنتاج تُرجع 404. غير مرتبطة من أي صفحة.

## النواقص والـ placeholders
- زر «متابعة طفلي»: معطل، لا صفحة ولا منطق له.
- لا زر خروج في أي صفحة (تسجيل الخروج لسه مش مبني).
- لا صفحة لإنشاء الدعوات (الاستهلاك مبني، الإنشاء بلا واجهة).
- لا صفحة لإدارة الفريق/الأدوار/الفروع (الحماية `guardAdminChange` بلا واجهة).
- الداشبورد يعرض «قريبًا» بدل الطلاب والمجموعات والحضور (غير مبنية).
- لا صفحة إعدادات ولا ملف شخصي.

# دليل الاختبار اليدوي من المتصفح

## كيف تقرأ هذا الملف
- خطوات تنفذها بنفسك بالترتيب من متصفحك.
- كل سيناريو: الخطوات، ثم النتيجة المتوقعة، ثم أين تتأكد في الداتابيز.
- كلمة collection تعني جدول في MongoDB.

## التشغيل
1. انسخ `.env.example` إلى `.env` واملأ `MONGODB_URI_DEV` (رابط Atlas أو محلي) و`AUTH_SECRET` (أي نص طويل).
2. `npm install` ثم `npm run dev` وافتح `http://localhost:3000`.
3. سجّل حسابين من `/register` (مالك ومعلم). روابط التفعيل تُطبع في الـ terminal على شكل `[DEV-MAIL] ... url=...` — انسخ الرابط والصقه.
4. ملاحظة: حسابات `seed-dev` (deva/devb) بلا كلمة مرور ولا تصلح للدخول — أنشئ حساباتك من الواجهة.

## السيناريوهات
1. **تسجيل ودخول**: سجّل حسابًا ← متوقع: دخول تلقائي إلى `/onboarding` وصف `users` فيه سطرك. افتح رابط التفعيل من الـ logs ← متوقع: «تم تفعيل بريدك» وحقل `emailVerifiedAt` امتلأ.
2. **إنشاء مركز**: فعّل الإيميل ثم «إنشاء مركز» (اسم + رقم مصري صحيح + برنامج واحد على الأقل) ← متوقع: `/dashboard` باسم مركزك. في الداتابيز: صف في جدول المراكز + صف «الفرع الرئيسي» في جدول الفروع + عضوية `center_admin` + صفوف البرامج.
3. **إنشاء بلا تفعيل**: حساب جديد غير مفعّل يحاول إنشاء مركز ← متوقع: رسالة «فعّل بريدك أولًا» ولا صف جديد في `orgs`.
4. **الدعوة والقبول**: من حساب المالك تحتاج كودًا — حاليًا لا واجهة لإنشائه (تولّده من دالة `createInvite` فقط). بالكود: سجّل حسابًا ثانيًا ← «عندي كود» ← أدخله ← متوقع: `/dashboard` بالدور المحدد، وفي جدول الدعوات صار `usedAt` ممتلئًا، وفي جدول العضويات عضوية جديدة.
5. **العزل**: سجّل حسابًا في مركزين مختلفين ← بدّل بينهما بزر «تبديل المركز» ← متوقع: كل مركز يرى فروعه وبرامجه فقط. كوكي `active_org` في أدوات المطور (Application → Cookies) يتغير مع التبديل.
6. **نسيان الباسورد**: `/forgot` بإيميلك ← انسخ رابط الـ logs ← عيّن باسوردًا ← متوقع: دخول بالجديد من `/login`.

## حالات الخطأ
- باسورد غلط ← «بيانات الدخول غير صحيحة أو الحساب موقوف» ولا دخول.
- إيميل مكرر في التسجيل ← «هذا البريد مسجل بالفعل».
- فتح `/dashboard` بلا دخول ← تحويل إلى `/login`. فتحه بحساب بلا مركز ← تحويل إلى `/onboarding`.
- كوكي `active_org` فاسد (عدّله يدويًا) ← تحويل إلى `/onboarding` (السياق يرفضه).
- كود مستخدم/منتهي ← «الكود غير صحيح أو منتهي أو مستخدم».

## ما يمكن اختباره الآن وما لا
- يعمل: التسجيل/الدخول/Google (بالمفاتيح)/التفعيل/الاستعادة/إنشاء مركز/القبول بكود/العزل/السمة والـ RTL.
- لا يعمل: زر الخروج (غير موجود)، إنشاء الدعوات من الواجهة، إدارة الفريق، بوابة ولي الأمر، أي شيء في كارت «قريبًا».

## التتبع
- الـ logs: الـ terminal الذي يعمل فيه `npm run dev` (روابط الإيميل تبدأ بـ `[DEV-MAIL]`).
- الكوكي: أدوات المطور ← Application ← Cookies ← `active_org` (معرف المركز) و`authjs.session-token` (الجلسة).
- الداتابيز: `mongosh "رابط-الاتصال"` ثم `show collections` لرؤية أسماء الجداول الفعلية (مثل users/orgs/memberships)، ثم `db.users.find()`.
