| تسجيل الخروج (زر) | يعمل (جهاز واحد) | `logoutAction` في قائمة المستخدم + مقارنة `sessionVersion` |

| هيكل الداشبورد (علوي+جانبي) | يعمل | `layout` + `sidebar` + `topbar` + مبدّلات + placeholders |

| الطلاب (نواة) | تعمل | قائمة + فورم + بطاقة + أرشفة/حذف/كود ولي أمر/صورة |
| تقارير التقدم | تعمل | ملخص + قائمة + إنشاء/تعديل/حذف + تزامن الموضع + عمود آخر تقرير |

| الاختبارات الآلية | تعمل (66 ناجحة) | `npm run test` (بعمال محدودة لتفادي تزاحم قواعد الذاكرة) |

## مشاكل وديون رأيتها (بدون إصلاح)
1. جلسات قديمة بلا `sessionVersion` تُرفض تلقائيًا بعد هذا التحديث (خروج إجباري مرة واحدة — مقصود).
2. تحقق `branchIds` في الـ schema يعمل عند الإنشاء فقط وليس التحديث المباشر — الأمان الحالي يعتمد على مرور كل كتابة عبر الـ services.
3. `guardAdminChange` يعدّ الأدمنز خارج transaction — سباق نظري موثق في الكود (`adminsVersion` موجود للحل لاحقًا).
4. `getPlatformStats` تقرأ كل المراكز دفعة واحدة — تكفي الآن وتحتاج ترقيم صفحات لاحقًا.
5. رابط التحقق/الاستعادة يُطبع في الـ logs خارج الإنتاج — أي وصول للـ terminal يعني اختراق حسابات (مقبول للتطوير فقط).
6. كود الدعوة يظهر في رابط الصفحة (`?created=`) بعد إنشائه — يبقى في سجل المتصفح (مقبول مقابل البساطة، والكود لمرة واحدة).

## الخطوات التالية المقترحة
1. **الطلاب والمجموعات**: الهدف أول كيان تعليمي. جداول + صفحات جديدة بالنطاق نفسه. البدء من `services/` جديدة وصفحات تحت `/dashboard`. سؤال: هل الطالب يُسجَّل برقم هاتف ولي الأمر من البداية؟
2. **دومين Resend موثق**: الهدف إيميلات حقيقية للجميع. توثيق دومين + `RESEND_FROM` عليه. سؤال: أي دومين/عنوان إرسال؟
3. **الحضور والتقدم**: بعد الطلاب والمجموعات. سؤال: الحضور يومي أم لكل جلسة؟
